# 구현 시작

현재 기능과 연결된 스펙을 읽는다. 목표가 비어 있으면 기능을 먼저 불러오도록 안내한다. 스펙에 선행 작업이나 구현을 막는 미정 사항이 있으면 실제 상태를 확인한다. 해결되지 않은 항목은 알리고 그에 의존하는 구현을 시작하지 않는다. 이미 사용자가 확정한 범위는 반복 확인하지 않는다.

1. 현재 프로젝트 위치, `git status`, 브랜치, HEAD를 확인한다. 기존 사용자 변경과 HEAD를 현재 기능의 작업 기준점에 기록한다.
2. `main` 작업 규칙을 지킨다. 다른 브랜치에서 안전한 전환이 불가능하면 기존 변경을 보존하고 이유를 알린다. 새 브랜치를 만들지 않는다.
3. 상태를 `진행 중`으로 바꾸고 수용 기준을 만족하는 최소 변경을 구현한다. 소스·DB 스키마·앱 설정은 `apps/web/`에, 스펙과 기록은 루트의 `context/`에 둔다.
4. 개발 소스가 없는 단계라면 첫 앱 생성 스펙을 따른다. 별도 React/NestJS 프로젝트나 원본의 제품 기능을 생성하지 않는다.
5. 필요한 검증을 Docker Node.js 24에서 실행한다. 실행 명령은 `docs/local-development.md`를 따른다. DB 변경은 로컬에서 마이그레이션으로 남긴다.
6. 변경 파일, 검증 결과, 아직 충족하지 못한 기준을 기록한다. 구현 중 요구사항이 달라지면 스펙도 동기화한다.

사용자가 구현까지 요청한 범위는 불필요한 재확인 없이 수행한다. 커밋·푸시·외부 배포는 별도 요청 범위를 따른다.
