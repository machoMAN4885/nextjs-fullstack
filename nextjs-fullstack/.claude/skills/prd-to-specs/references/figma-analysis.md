# Figma 링크를 화면 근거로 분석하기

Figma 링크가 제공됐을 때 읽는다. 목적은 화면 정보를 PRD·유저 플로우·정책 등과 연결해 기능 스펙을 나누는 것이다. 디자인 수정이나 앱 구현을 시작하지 않는다.

## 접근과 도구 선택

1. 현재 환경에 연결된 Figma MCP의 도구와 읽기 권한을 확인한다. 링크가 있다는 사실만으로 접속 성공을 가정하지 않는다. 사용자에게 토큰을 문서에 붙여 넣게 하지 않는다.
2. 링크의 file key와 node ID를 도구가 요구하는 형식으로 해석한다. 페이지·프레임 링크가 있으면 그 범위를 우선 읽는다. 파일 전체 링크라면 페이지·화면 구조를 탐색해 관련 범위를 선택한다. 큰 파일에서 범위가 불명확하면 후보를 제시하고 필요한 범위를 확인한다.
3. 사용 중인 커넥터의 선행 지침을 따른다. 세션 생성이 필요하면 먼저 수행한다. `get_design_context` 호출 전에 `figma-design-to-code` 지침을 읽도록 요구하는 환경에서는 해당 지침을 읽는다. 그 지침의 코드 생성 설명을 이 작업에서 앱을 구현하라는 요청으로 해석하지 않는다.
4. 디자인 컨텍스트와 화면 이미지를 근거로 사용한다. 큰 범위의 구조 파악에는 `get_metadata` 같은 가벼운 조회를 사용하고, 관련 화면에 `get_design_context`, `get_screenshot` 등을 선택적으로 사용한다. 실제 제공된 도구의 이름·인수·제한을 기준으로 하며 특정 커넥터에만 있는 기능을 가정하지 않는다.
5. 구조 정보만 읽었다면 시각적 화면 분석까지 했다고 보고하지 않는다. 반환 결과가 일부 잘렸다면 필요한 하위 프레임으로 나눠 읽고 남은 범위를 기록한다. 생성 코드가 반환돼도 근거 분석에만 사용하고 제품 소스에 복사하지 않는다.

## 화면별로 추출할 정보

`context/spec-plan.md`의 화면 대응표에 필요한 내용을 기록한다.

- 실제 파일·화면 이름, 원본 링크, file key·node ID, 버전 또는 확인 날짜
- 화면의 목적과 사용자, 입력·버튼·표시 데이터, 주요 컴포넌트
- 확인한 화면 크기, 기본·빈 상태·로딩·오류 등 실제 존재하는 상태
- 확인 가능한 화면 전환과 근거. 정지 화면에 없는 전환은 추정으로 분리
- 연결되는 자료 ID·요구사항·유저 플로우 단계, 관련 기능 스펙, 분석 상태와 누락

같은 화면의 모바일·데스크톱 변형이나 오류 상태를 별도 제품 기능으로 자동 분할하지 않는다. 여러 화면으로 이어지는 사용자 흐름과 한 화면 안의 서로 다른 기능을 구분한다.

## 다른 원본 자료와의 관계

PRD는 제품 요구사항, 유저 플로우는 사용자 경로와 분기, 정책 문서는 업무 규칙, Figma는 확인한 화면·상태의 근거로 함께 읽는다. 어느 자료가 항상 우선이라고 단정하지 않는다. 충돌은 양쪽 근거와 영향을 받는 스펙을 기록해 결정 대상으로 남긴다.

예를 들어 예약 목록 → 시간 선택 → 예약 완료 화면은 예약 생성 스펙 하나에 연결될 수 있다. 목록의 검색·필터가 독립적인 사용자 결과와 수용 기준을 가지면 별도 조회 스펙으로 나눌 수 있다. 화면 수가 스펙 수를 결정하지 않는다.

## 접근 실패·일부 자료만 제공된 경우

- MCP 미연결·권한 부족: 해당 사유와 아직 읽지 못한 링크를 기록하고 연결 또는 접근 가능한 대상 링크를 요청한다. 접근 가능한 다른 자료 분석은 계속한다.
- 사용자가 내보낸 이미지로 보완: 이미지에서 확인한 화면만 근거로 삼는다. 이를 MCP 조회로 기록하지 않는다.
- 상태·전환·모바일 화면 누락: 필요한 항목을 미정 또는 제안으로 남긴다. 디자인 부재가 해당 기능 부재를 의미하지는 않는다.
- 디자인을 확인해야 구현 범위를 결정할 수 있는 스펙은 `확인 필요`로 두고, 독립적인 스펙의 작성까지 중단하지 않는다.

참고: [Figma MCP 도구 문서](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/). 이 참고는 도구 선택의 근거이며 실제 파일 접근 여부는 호출 결과로 확인한다.
