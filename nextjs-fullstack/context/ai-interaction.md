# AI 협업 규칙

## 작업 흐름

기존 PRD·유저 플로우·정책 등 여러 문서나 자료 폴더에서 시작할 때는 `prd-to-specs`로 전체 분해 계획과 개별 스펙 초안을 작성한다. 폴더는 하위 자료까지 읽고 자료 목록·확인 범위·충돌을 기록한다. Figma 링크가 있으면 MCP로 관련 화면을 읽고 요구사항·사용자 흐름에 연결한다. 사용자가 범위·순서·미정 사항을 검토한 뒤 아래 흐름으로 구현한다.

1. 기능의 사용자·문제·범위·수용 기준을 `context/features/<기능명>-spec.md`에 기록한다.
2. `context/current-feature.md`에 스펙 경로, 목표, 검증 계획을 불러온다.
3. 스펙의 합의된 범위를 구현한다. 필요한 설명은 짧게 하고, 서비스 범위를 바꾸는 미정 사항은 확인한다.
4. 요구사항과 결과를 대조하고 필요한 테스트, 타입 검사, 린트, 빌드, 사용자 흐름 확인을 수행한다.
5. 발견한 문제를 수정하고 변경에 영향을 받는 검증을 다시 실행한다.
6. 검증 근거를 남기고 완료 이력을 맨 아래에 추가한다.

스펙·설계·완료 이력은 한국어로 쓴다. 문서에는 계획과 실제 구현을 구분한다. 기존 기능이 없는 템플릿을 완성된 서비스로 보고하지 않는다.

## Git

- 이 저장소는 `main`에서 작업한다. 기능 브랜치 생성·병합·삭제 절차를 추가하지 않는다.
- 커밋과 푸시는 사용자가 요청한 경우에 수행한다. 현재 요청이 이미 허용했다면 같은 확인을 반복하지 않는다.
- 다른 브랜치에 있다면 작업 트리와 변경사항을 먼저 확인한다. 안전하게 전환할 수 없으면 이유를 알리고 기존 변경을 보존한다.
- 커밋은 작업 범위의 파일만 선택한다. 상위 저장소 전체를 `git add .`로 묶지 않는다.
- `feat:`, `fix:`, `docs:`, `chore:` 등 목적이 드러나는 메시지를 쓴다. AI 공동 작성자 표시를 자동으로 넣지 않는다.
- 기능 변경 시 관련 검증이 통과해야 커밋한다. 문서만 바뀐 경우 문서·링크 검증이면 충분하다.

## 데이터와 운영

- 기본 개발 DB는 로컬 Docker PostgreSQL이다. Neon 연결은 개발·미리보기·운영 환경을 명확히 구분한다.
- 실서비스 DB에 로컬 테스트나 초기화를 실행하지 않는다. 마이그레이션은 로컬에서 작성·검증하고 운영에는 `migrate deploy`로 적용한다.
- `.env`와 실제 연결 문자열을 Git, 보고서, 로그에 남기지 않는다. 환경 변수 점검은 이름만 비교한다.
- 배포·운영 데이터 변경은 사용자가 요청한 대상과 범위에서만 수행한다.

## 검증과 문제 해결

같은 가정으로 반복 실패하면 원인·오류·다음 조사 방향을 정리한다. 무관한 리팩터링이나 새 기능으로 해결 범위를 넓히지 않는다. 실행한 명령, 결과, 실행하지 못한 항목을 구분한다. 테스트가 없으면 없다고 쓰며 빈 테스트 성공을 만들지 않는다.
